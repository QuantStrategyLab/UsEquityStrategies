# Phase 2: Settled Transfer Funding Gate

The existing two-member `auto_allocate.py` remains a bounded scenario budget search. An optional `settled_transfer_funding` input now restricts its candidate budgets using actual free settled cash supplied by the account replay. The legacy input and output are unchanged when this field is absent. This gate does not introduce a new capital-curve formula, new risk preference, or a trade executor.

An optional `fixed_member_weights` input evaluates exactly one caller-supplied two-member budget through the same locked-asset, capital-curve, stress-loss, fee, and settled-funding checks. Its reported log-growth objective is descriptive; the allocator does not optimize the fixed weights. An explicitly supplied field must contain both valid member weights; null and incomplete values fail closed. The caller must freeze the weights before the evaluation window, since this function cannot establish how they were chosen. The residual budget remains outer cash after the transfer fee; weights summing to one can therefore be infeasible when a fee is due. No fixed allocation is supplied as a default.

For each member, a proposed budget reduction must not exceed that member's free settled cash. The sum of proposed member increases and the one-time transfer fee must not exceed free settled outer cash plus those funded reductions. Free settled cash excludes security value, member reserves, unsettled sale proceeds, dividend receivables, collateral, and other locked amounts. The candidate still satisfies `B_SOXL + B_TQQQ + CASH + fee = NAV`; `CASH` is a budget-account value and can include amounts that are not yet spendable, while `free_cash_usd.CASH` is the presently transferable subset.

The synthetic cash-only continuous builder path supplies each member's marked cash and outer cash to this gate before daily transfers. That fixture excludes options, restricted cash, dividends, and external events; it does not independently certify a sale-settlement date or member reserve. A direct regression shows the difference: with $100 in member A securities and no settled cash, the old instantaneous budget search can propose moving $100 to member B; the new funded search retains A until cash becomes available. When A instead has $100 free settled cash, the transfer can be proposed. The allocator's nonzero transfer-fee funding check is tested separately; the continuous demo still accepts only zero transfer fee. The result remains `MECHANISM_APPROXIMATION`: member builders, whole-share trades, actual sale timing, pending-settlement release, fees, and the joint ledger must still be checked in the existing replay. No historical full-v2 result or execution permission follows from this gate.

## Fixed-budget continuous-builder check

`small_account_demo.run` now accepts caller-supplied `fixed_member_weights` and passes them unchanged through the existing allocator, settled-funding gate, two original member builders, whole-share execution and QPK ledger readback. The default call remains the automatic-search path. In one artificial three-session fixture, the fixed comparator uses only the first decision's automatic budgets (`SOXL=$600`, `TQQQ=$9,400`, current NAV `$10,000`) to freeze weights of 0.06/0.94 before either later session. It does not select weights using the terminal outcome.

Both paths start with the same budget and first two account marks. On the second decision, automatic search chooses `SOXL=$800`, `TQQQ=$9,100`, outer cash `$99.50`; the fixed input requests `SOXL=$599.97`, `TQQQ=$9,399.53`, outer cash `$0` from that day's `$9,999.50` NAV. Both requests pass the same available-cash transfer checks and real member builders. Their final whole-share holdings differ, while this particular artificial final mark gives both `$9,894.445` NAV. That equality is a fixture outcome, not proof of strategy equivalence, historical return, optimality or a risk-policy choice. Perturbing the final synthetic price does not alter either earlier fixed-budget transfer. The separate synthetic sell-first path remains an explicitly dated scenario, not a generic settlement engine.
